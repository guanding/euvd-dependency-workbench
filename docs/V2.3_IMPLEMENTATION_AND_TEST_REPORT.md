## P1 / PRE-7 证据设计

CycloneDX 导入保留 `specVersion`、`serialNumber`、BOM `version`、metadata、原始
components、dependencies、PURL/CPE/bom-ref、hash 和关系。PRE-7 摘要只输出：

- `[PRE-7-RQ-06]` Author/Version/Timestamp/tools 的可观察字段与缺口；
- `[PRE-7-RQ-07]` producer/name/version/identifier/dependency/hash 的逐项覆盖；
- `automatic_conformity_decision=false`。

这不能单独证明产品组件总体完整性、供应商哈希 RE 已激活或实际发布制品一致。
原始 SBOM 按 SHA-256 保留，任务 JSON 仅持久化紧凑摘要；CycloneDX JSON
上限 10 MB、任务组件上限 2,000、解析嵌套深度上限 100，超限在上传记录持久化前拒绝。

首次 JSON E2E 揭示原始 SBOM 与紧凑上传记录曾解析到同一
`<upload_id>.json` 路径，原始证据被覆盖；该次结果已标为 `FAILED` 并保留。
修正后记录改为 `<upload_id>.upload-record.json`，老记录仅作兼容回读；
重封 E2E 必须单独核对原始文件 SHA-256。

## P2 / P3 生成器和自测

扫描器：Syft 1.50.0，镜像
`anchore/syft@sha256:1288ea4c8b38767b4e620c1e312c8cb26b6e887a99b4f07ab6cd19fc6f225026`。

控制：显式指定唯一 Compose 文件并移除继承 override；同时核对渲染配置和
实际退出容器的 `network_mode:none`、非 root、只读输入/根文件系统、capabilities 全部
drop、无 Docker Socket 及扫描器镜像 ID。对账必须同时校验 generation、input manifest、
scanner control、Syft JSON 和 CycloneDX 的 SHA-256 绑定。
对账时还会重算当前 source/portable 目录的 exact-set 输入 manifest，防止生成后文件漂移被误判为 PASS。
Docker archive 另解析 OCI `index.json -> platform manifest -> config` 链，由 archive
根 descriptor 导出 Docker image ID，必须与执行 `docker image inspect` 时显式
传入的期望 image ID 一致。

P3 调试期曾遇到非 root 不能写 `/tmp`，修正 tmpfs 为 `mode=1777` 后保留
`noexec/nosuid`。首次 archive 身份实现又错把 config digest 当成 Docker image ID，
该次 fail-closed 证据同样保留；修正为 OCI 根 descriptor 后以新身份重跑。
最终封存前还发现宿主 `__pycache__` 进入过渡镜像，通过递归 `.dockerignore`
规则清除并重建；运行镜像中此类缓存文件计数为 0。

三身份初始对账：

- source：8 个 CycloneDX 组件；
- Linux image：1,850 个（含 1,798 个 file 组件）；
- Windows portable：147 个；
- source 和 image 均发现 7/7 锁定直接依赖；
- portable 同时发现 fastapi、packaging、python-multipart、starlette、uvicorn 的
  旧版本元数据，状态 `REVIEW`。
