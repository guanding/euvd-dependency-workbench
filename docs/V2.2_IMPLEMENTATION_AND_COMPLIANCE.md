# EUVD Dependency Workbench v2.2 实施与合规映射

## 1. 版本定位

v2.2 是制造商内部的 SBOM 漏洞调查、产品适用性、证据和 CRA Article 14
报告准备工作台。它不作自动法律判定，不代表 TÜV/公告机构合格评定结论，也不
自动向 ENISA Single Reporting Platform（SRP）提交数据。

当前法规基线：

- Regulation (EU) 2024/2847（Cyber Resilience Act）；
- ENISA SRP FAQ，网页标注更新于 2026-07-17；
- 项目冻结的 prEN 40000-1-3 CEN Enquiry draft，仅作工程流程和证据设计输入，
  不是已发布协调标准，不能据此主张 CRA 符合性推定。

## 2. 法规与实现映射

| 法规/标准依据 | v2.2 控制 | 证据输出 | 边界 |
| --- | --- | --- | --- |
| CRA Art.3(42) | `reportable` 需要产品 `known_affected`，并绑定恶意行为者、未经许可、实际利用、产品相关性、来源和 SHA-256 均完整的结构化证据 | evidence + audit event + 双人决定 | EUVD/KEV 命中只能触发调查，不能单独形成最终判定 |
| CRA Art.14(1) | 为积极利用漏洞建立独立案件，支持无 CVE/EUVD 的 zero-day | case、产品/build/SBOM hash、证据链 | 工具不覆盖 Art.14(3)-(5) 严重安全事件报告流程 |
| CRA Art.14(2)(a) | 人工确认制造商 awareness；计算不无故拖延且最迟 24h | awareness 依据、证据引用、确认账户、24h deadline | 扫描时间、KEV 日期和外部信号时间均不自动成为 awareness |
| CRA Art.14(2)(b) | 计算最迟 72h；检查一般信息、漏洞/利用性质、修正措施和用户措施 | 72h SRP JSON/XLSX/HTML 草稿 | 敏感性字段按 ENISA Q16 的 “有信息时必填” 提示，不伪造值 |
| CRA Art.14(2)(c) | 修正或缓解措施可用后计算 14 日；检查完整描述、严重性、影响和更新详情 | Final SRP 草稿和回执 | 未设置修正措施可用时间时，最终期限保持未启动 |
| CRA Art.14(7) | SRP 草稿保留 CSIRT coordinator 字段 | SRP draft | v2.2 不自动选择具有法律效力的协调 CSIRT |
| CRA Art.16 | 仅生成分阶段草稿并登记人工提交回执 | early-warning / notification / final-report receipt | 不连接 SRP；ENISA FAQ Q15 表示目前不提供 API |
| CRA Annex I Part II §1 | 保存 SBOM 来源文件名、格式、版本、SHA-256 与产品/build 绑定 | `sbom_snapshots` | 工具不验证 SBOM 已覆盖制造商全部组件 |
| CRA Annex I Part II vulnerability handling requirements | 案件跟踪适用性、风险、修正措施、复核日期和审计事件 | cases/evidence/approvals/audit | 工具是记录载体，不能代替制造商漏洞处理过程的有效性证据 |
| prEN 40000-1-3 PRE-7 | SBOM 身份及版本/build/hash 变化使未提交结论失效并重开 | `stale_reason`、`reporting_stage=reopened` | 草案参考 |
| prEN 40000-1-3 RCP-2/RCP-3 | 公开数据监测与受影响软件识别 | EUVD/KEV snapshot、产品适用性 | 公共未命中不等于无利用 |
| prEN 40000-1-3 VRF-1/VRF-2 | 初步验证与风险评估关口 | initial assessment、risk summary、evidence | 人工证据质量负责 |
| prEN 40000-1-3 RLS-2/PRA-1 | 修正发布信息和发布后复核 | corrective measure、user measures、next review | 草案参考 |

## 3. SRP Q16 字段实现

v2.2 按 ENISA SRP FAQ Q16 的漏洞报告列实现：

- 24h：强制检查通知类型、通知级别、制造商/开源 steward 名称、产品和标题；
- 72h：继承并检查产品类型、可用成员国、一般信息、漏洞一般性质、利用一般
  性质、已采取修正/缓解措施和用户措施；
- Final：继承前序信息，并检查措施可用日期、完整漏洞描述、严重性、影响和
  安全更新/修正措施详情；
- 产品类型非 `Default` 时要求 Annex III/IV 产品类别；
- CVE、EUVD、恶意行为者及敏感性按 Q16 的 Optional / If available 语义保留，
  不为通过校验而制造事实；
- `reporting time` 和 `reporter` 在 ENISA 表中为平台自动字段，草稿不强制用户
  手工填写。

## 4. 四眼和身份边界

技术审批只保存提议，不写入最终 `art14_decision`。第二个不同本地审批账户进行
合规复核且决定一致后，案件才进入 `approved`。不一致时保持
`not_assessed/compliance_review`。审批 PIN 使用带随机 salt 的 scrypt hash。

这是单机审批账户分离，不是完整身份认证。现实身份、制造商授权、职责分离和
电子签名应由组织程序另行证明。当前部署必须保持本机访问；共享部署前必须增加
SSO/RBAC/TLS/备份和授权撤销。

## 5. VEX

- 导入：CycloneDX 1.7 VEX JSON、CSAF 2.0 VEX Profile JSON；
- 状态：`under_investigation`、`known_affected`、`known_not_affected`、`fixed`；
- `known_not_affected` 缺少产品级理由时降级为 `under_investigation`；
- 同一漏洞/产品出现冲突状态时拒绝导入；
- zero-day 没有 CVE 时不生成虚假的 `CVE-UNKNOWN`；
- 导出结构已针对 CycloneDX 1.7 和 CSAF 2.0 官方 JSON Schema 做实测校验。

## 6. 数据源与降级

公共数据记录 `downloaded_at`、本次 `checked_at`、age、SHA-256、记录数和状态。
状态语义：

- `fresh`：在配置的更新时间内；
- `stale`：已超过更新时间；
- `degraded`：更新失败，使用 last-known-good；
- `unavailable`：没有可用快照。

任何非 fresh 状态均不得把 “未命中” 解释为当前没有公开利用信号；即使 fresh，
未命中也不构成 “未被利用” 结论。

## 7. 数据库与审计

`data/workbench.sqlite3` 使用 WAL 模式，保存 SBOM 快照、案件、证据、审批、
awareness、分阶段回执、VEX 导入、feed 状态和哈希化审计事件。v2.1 扫描 JSON
不被重写；v2.2 启动时幂等登记已完成扫描的 SBOM 身份。

审计日志用于变更追踪，不是防篡改账本：本机管理员仍可修改文件。需要强防篡改
时，应把日志推送到受控的远端 WORM/SIEM。
